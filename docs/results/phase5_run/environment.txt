Methodology
-----------
* Operations are pre-generated (deterministic from the seed) so generation, parsing and I/O are never timed.
* Each pass uses a fresh MatchingEngine. Prefill + warm-up operations run first, untimed; only the
  measured segment is recorded. 'Event' in events/sec means one input command (submit or cancel).
* Throughput pass: the whole measured segment is timed once with std::chrono::steady_clock; no per-op clock reads.
* Latency pass: each operation is timed individually (two steady_clock reads). The cost of the clock
  itself is reported as timer_overhead_ns; latencies below a few multiples of it are not meaningful.
* Percentiles use nearest-rank on the sorted samples and are reported only when at least 10 samples lie
  above them (p99 needs >= 1,000 samples; p99.9 needs >= 10,000). Otherwise the cell is left empty.
* Allocation pass: global operator new/delete are counted during the measured segment; peak_live_bytes uses
  malloc_usable_size (glibc; excludes malloc headers/rounding). heap_in_use_bytes uses mallinfo2 and includes them;
  heap_after_drain_bytes is the same after every resting order has been cancelled.
* Repetitions re-run the identical operation list; the spread across reps shows run-to-run noise.
* With both engines, repetitions are interleaved and the first engine alternates each rep, so machine drift
  does not systematically favour one implementation. Compare engines using the PAIRED ratios per rep.
* Builds with assertions enabled or sanitizers are flagged valid_for_comparison=0 and must not be
  compared with optimised builds. Frequency scaling / turbo / noisy neighbours are NOT controlled
  unless you pin the CPU and fix the governor yourself.
